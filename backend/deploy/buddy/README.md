# Buddy: чат, Qwen и встроенный MCP

Отдельный Go-сервис с PostgreSQL 16 и OIDC-клиентом `buddy`. Предоставляет JSON API и SSE;
интерфейс React добавляется следующим этапом. Одна реплика сервера: при старте незавершённые
запуски и подтверждения переходят в ошибку, без автоматического повтора операций.

Из корня репозитория:

```sh
cd backend/deploy/buddy
cp .env.example .env
# Указать отдельный пароль БД, секрет существующего OIDC-клиента buddy,
# зарегистрированный HTTPS callback, публичный адрес Wiki и общий BUDDY_API_KEY.
docker network create ai-buddy-shared # если сеть ещё не создана
docker compose up -d --build
```

Контейнер сервера слушает `127.0.0.1:8081` на хосте; HTTPS и проксирование настраиваются снаружи.
База и миграции находятся в приватной сети, сервер также подключён к `ai-buddy-shared`.
Порт PostgreSQL наружу не опубликован, данные хранятся в отдельном томе.
Нужны запущенные Tracker, Ticket, Wiki и [Ollama](../ollama/README.md) с `qwen3.5:4b`.
`BUDDY_API_KEY` должен совпадать в Buddy и трёх сервисах. Административный токен Authentik
и отдельный seed чатов не используются. Для Wiki нужен его собственный токен чтения пользователей.

Локальный запуск из `backend` (экспортировать переменные из `.env` и указать доступный `DATABASE_URL`):

```sh
go run ./cmd/migrate buddy up
go run ./cmd/buddy
```

Health endpoints: `GET /health/live`, `GET /health/ready` (проверяет БД).
Вход: `GET /api/auth/login`, callback `/api/auth/callback`, `GET /api/auth/me`,
`POST /api/auth/logout`. Защищённая cookie сессии требует HTTPS.
Все предметные маршруты доступны только стажёру: без сессии `401`, наставнику `403`,
для чужих объектов `404`. Защита браузерных POST от cross-origin запросов общая с платформой.

## API

| Метод и маршрут | Запрос | Ответ |
|---|---|---|
| `POST /api/chats` | без тела | `201`: `id`, `title`, `created_at` |
| `GET /api/chats` | — | `200`: `chats` |
| `GET /api/chats/{id}` | — | `chat`, `messages`, `runs`, `latest_run`, `actions`, `cards` |
| `POST /api/chats/{id}/messages` | `{"content":"Как оформить доступ?"}` + `Idempotency-Key` | `202`: запуск |
| `GET /api/runs/{id}/events` | необязательный `Last-Event-ID` | `text/event-stream` |
| `POST /api/runs/{id}/retry` | без тела | `202`: новый либо уже созданный повтор |
| `POST /api/actions/{id}/confirm` | `{"fields":{...}}` либо `{}` | `200`: состояние действия и результат сервиса |
| `POST /api/actions/{id}/cancel` | без тела | `200`: отменённое действие |

Запуск: `id`, `chat_id`, `status`, `error`, `events_url`. Состояния: `queued`, `running`,
`done`, `error`. В чате один активный запуск; параллельное новое сообщение даёт `409`.
Ключ сообщения обязателен, до 200 байт; повтор с тем же текстом возвращает тот же запуск,
с другим текстом — `409`. Текст сообщения — до 2000 символов; если текущий запрос со
схемами инструментов не помещается в консервативный бюджет контекста, запуск завершится
ошибкой с просьбой сократить текст. Название чата — первые 80 символов первого сообщения.
Повтор ответа не создаёт второе сообщение пользователя. Повтор `retry` для одного запуска
возвращает тот же дочерний запуск; если он тоже завершился ошибкой, повторять его ID.

SSE-события имеют последовательный числовой `id` в рамках запуска и JSON в `data`:

- `stage`: строка (`waiting_for_model`, `choosing_tools`, имя инструмента, `answering`);
- `text`: строка с очередным фрагментом ответа;
- `source`: источник из Wiki (ID документа, заголовки, фрагмент, абсолютный URL);
- `action`: карточка черновика (`id`, `kind`, `status`, `fields`);
- `result`: ответ Tracker о завершении задачи;
- `usage`: фактический `prompt_eval_count` от Ollama и `num_ctx: 4096`;
- `done` / `error`: объект `status`, `error`.

Сначала сохраняется событие и фрагмент ответа, затем клиент получает их при опросе БД
каждые 250 мс. Heartbeat — комментарий каждые 15 секунд. Отключение клиента не отменяет
генерацию. `Last-Event-ID: 4` воспроизводит события с ID > 4, в том числе после завершения.
История включает сохранённый текст при сбое, источники/результаты в `cards` и все действия.

## Подтверждения и инструменты

`create_task` и `create_ticket` сохраняют только черновик. Поля задачи: `title`
(1–200 символов), `description` (до 10000), `deadline` (`YYYY-MM-DD`). Поля тикета:
`question` (1–200), `description` (1–10000). Подтверждение может заменить поля черновика;
после начала выполнения они неизменяемы. Состояния действия: `draft`, `executing`, `done`,
`error`, `cancelled`. Отмена разрешена до начала выполнения. Одновременное подтверждение
даёт `409`; повтор завершённого подтверждения возвращает сохранённый результат.
При `error` повторить `confirm` с `{}` либо с теми же полями. Используется прежний ключ
`buddy-action:<action-id>`, включая потерянный ответ сервиса. Результат операции берётся
из Tracker/Ticket и не требует нового запроса модели. Ошибка операции находится в карточке.

Шесть инструментов объявлены только на приватном MCP-сервере официального Go SDK:
`search_documents`, `get_progress`, `create_task`, `complete_task`, `create_ticket`,
`list_tickets`. На каждый запуск создаётся in-memory MCP-сессия с замыканиями на доверенного
пользователя. Публичного MCP endpoint нет. Схемы Ollama получаются через `tools/list`;
вызовы выполняются через `tools/call`. ID пользователя, команда, ключ и подтверждение
не принимаются в аргументах. Подтверждённая запись вызывается Go-кодом через тот же слой.

Завершение задачи дополнительно проверяет свежий список собственных задач и точную явную
команду текущего пользователя: `Заверши задачу <ID или название>` / `Complete task <ID or title>`
(также `Заверши ...` / `Complete ...`, кавычки и точка допустимы). Совпадение должно быть
единственным; иначе модель получает требование уточнить задачу. Инструкции из найденного
документа не могут дать это разрешение. Более свободную формулировку пользователь уточняет.

Wiki получает ID пользователя, сам определяет его актуальную команду и возвращает доступные
фрагменты. Ссылки формируются исключительно из Wiki и `WIKI_PUBLIC_URL` (пока JSON API).
Пустая выдача отличается от ошибки; агенту передаётся предложение обратиться к наставнику
и признак наличия назначения. Внутренние процессы и инструменты направляются в Wiki
системной инструкцией; содержимое документов рассматривается как недоверенные данные.

## Ограничения и проверки

Qwen: нативный `/api/chat`, `qwen3.5:4b`, `think:false`, `num_ctx:4096`,
`num_predict:512`. Выбор инструментов без streaming, до шести вызовов последовательно;
финальный streaming-запрос без инструментов. Один запуск занимает слот модели, остальные
показывают `waiting_for_model`. Полная история остаётся в БД; в модель идут последние
завершённые обмены и сокращённые результаты. Бюджет консервативно считает UTF-8 байты
вместе со схемами и резервирует 512 токенов ответа плюс 128 на обрамление; сначала удаляет
старые обмены, затем сокращает результаты и старые раунды инструментов. Фактическое число
токенов возвращается событием `usage`.

Таймауты: запуск 10 минут, запрос Ollama 5 минут, Wiki 90 секунд, Tracker/Ticket 10 секунд.
Для HTTP-подтверждения выделено до 30 секунд независимо от отключения браузера.
Чтение истории не обращается к Ollama. Брокер, память агента, суммаризация, вложения,
удаление и переименование чатов не добавлены.

Полная проверка (из `backend`) использует отдельную PostgreSQL 16 с pgvector для существующих
Wiki-интеграций. Тесты создают и удаляют изолированные схемы; роль должна иметь права на
создание схем и расширения vector. Не указывать рабочую базу.

```sh
TEST_DATABASE_URL=postgres://user:password@localhost:5432/test?sslmode=disable ./scripts/check.sh
```

Скрипт запускает форматирование, vet, сборки, race-тесты, отдельные группы покрытия
Tracker/Ticket/Wiki/Buddy/Platform со строгим порогом >80% и Compose validation.
Обычный запуск требует `TEST_DATABASE_URL` и Docker CLI; `./scripts/check.sh --unit` явно отключает PostgreSQL-интеграции и пороги покрытия.

Реальные Qwen и Wiki embeddings проверяются отдельным тестом на изолированных схемах:

```sh
TEST_DATABASE_URL=postgres://user:password@localhost:5432/test?sslmode=disable \
BUDDY_REAL_OLLAMA_URL=http://127.0.0.1:11434 \
go test -v -timeout 30m ./internal/buddy -run '^TestRealQwenFlow$'
```

Тест индексирует небольшую базу знаний обеих команд настоящей EmbeddingGemma и проверяет
Qwen → Wiki → ответ с карточками, прогресс, подтверждение задачи, потерянный ответ при
создании, повтор без дубля, завершение задачи и тикет наставнику. Вывод содержит задержку
каждого запуска и фактический размер финального контекста; проверяется резерв ответа.
Для детерминированного сквозного теста с настоящими HTTP API и PostgreSQL, но без моделей,
использовать `-run '^TestServiceFlow$'`. MCP SDK: [официальный репозиторий](https://github.com/modelcontextprotocol/go-sdk),
Ollama: [нативный chat API](https://docs.ollama.com/api/chat).

Исходная реализация проверена 14 ноября 2026 года (до финализации API): весь сквозной сценарий с настоящими моделями прошёл
на AMD Ryzen 5 7500F (6 ядер / 12 потоков), Ollama 0.40.16 из официального пакета Arch,
`100% CPU`, `qwen3.5:4b` digest `d8b0f5e9760c`, EmbeddingGemma digest `85462619ee72`.
Для измерений использовался временный CPU runtime на loopback и PostgreSQL 16 с pgvector
в Docker; это не измерение производительности публичного OIDC-деплоя.

Максимальный prompt среди всех 19 запросов Qwen — 1083 токена; runner подтвердил контекст
4096 и отсутствие truncation. Время включает выбор инструментов, HTTP API и финальный
streaming, но не загрузку моделей. Подтверждения выполнялись отдельно без Qwen; тест
подтвердил отсутствие повторной задачи после потери ответа Tracker и повторного confirm,

Platform 97,26%; race, vet, сборки и все Compose validation прошли.
