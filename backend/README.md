# Backend

Минимальный Go-бэкенд. Конфигурация читается из окружения через cleanenv:

| Переменная | Значение |
| --- | --- |
| `ADDR` | Адрес HTTP-сервера, по умолчанию `:8080` |
| `DATABASE_URL` | Обязательный URL PostgreSQL |
| `KNOWLEDGE_BASE_DIR` | Путь к базе знаний, по умолчанию `../knowledge-base` |
| `OLLAMA_URL` | Адрес Ollama, по умолчанию `http://localhost:11434` |
| `EMBEDDING_MODEL` | Модель эмбеддингов, по умолчанию `embeddinggemma:300m` |
| `CHAT_MODEL` | Диалоговая модель, по умолчанию `qwen3.5:4b` |
| `CHAT_CONTEXT_LENGTH` | Окно контекста Ollama в токенах, по умолчанию `16384`; положительное число |
| `CHAT_HISTORY_LIMIT` | Число последних сообщений для модели, включая текущий вопрос, по умолчанию `6`; положительное число |
| `SYSTEM_PROMPT_FILE` | Файл системного промпта, по умолчанию `prompts/buddy.md` |
| `RAG_CHUNK_COUNT` | Максимальное количество результатов поиска, положительное целое, по умолчанию `3` |

## Docker Compose

Из каталога `backend/`:

```sh
docker compose up --build -d
docker compose logs server migrate
```

Compose ждёт готовности PostgreSQL, применяет миграции отдельным сервисом
`migrate`, дожидается подготовки диалоговой модели и запускает сервер на порту 8080.
Сервис `ollama-chat-model` после готовности Ollama проверяет `CHAT_MODEL`
и скачивает её, если она отсутствует. При ошибке загрузки сервер не запускается.
Первая загрузка может занять время; модель сохраняется в volume Ollama. PostgreSQL 16 использует образ
`pgvector/pgvector:pg16` с расширением `vector`. Список пользователей доступен
по `GET /api/users`. База доступна локально на `127.0.0.1:5432`.
Для нового бэкенда используется отдельный volume `buddy-backend_postgres`.
Порт 8080 должен быть свободен от прежнего бэкенда.

Повторно применить миграции:

```sh
docker compose run --rm --build migrate
```

Для добавления `00004_tickets.sql` и `00005_message_tickets.sql` достаточно применить миграции; существующие
данные сохраняются. При изменении или перенумерации прежних миграций нужно сбрасывать БД,
удаляя только volume PostgreSQL, и затем заново применять миграции и сид
(volume Ollama с загруженной моделью сохраняем):

```sh
docker compose down
docker volume rm buddy-backend_postgres
docker compose up --build -d
docker compose run --rm --build seed
docker compose run --rm --build index
```

## Локальный запуск

Из каталога `backend/` (нужен Go 1.27):

```sh
docker compose up -d postgres
set -a
. ./.env.example
set +a
go run ./cmd/migrate
go run ./cmd/server
```

Программа сама не загружает `.env`-файлы. `.env.example` содержит только локальные
значения; Compose использует `POSTGRES_PASSWORD` из окружения или `.env`
(по умолчанию `buddy`). При смене пароля нужно также обновить локальный `DATABASE_URL`.

Миграции лежат в `migrations/` и выполняются goose по порядку. Команду
`cmd/migrate` нужно запускать из `backend/`. Миграции сгруппированы по предметным областям:

- `00001_users.sql` — пользователи и связи стажёр–ментор.
- `00002_wiki.sql` — документы, чанки и pgvector.
- `00003_chats.sql` — чаты, сообщения и источники сообщений.
- `00004_tickets.sql` — созданные тикеты с автором и временем PostgreSQL.
- `00005_message_tickets.sql` — карточки тикетов, привязанные к сообщениям Buddy.

После объединения миграций прежнюю БД нужно пересоздать по инструкции выше.

## Пользователи и сидирование

Пакет `internal/users` содержит сущность `User` с полями `ID`, `Name`, `Role`,
`Team`. HTTP-хендлер находится в `internal/users/handler/handler.go`.
PostgreSQL-репозиторий `users.Repository` находится
в `internal/users/repository/repository.go`: `Add`, `Get`, `List`. ID задаёт вызывающий код;
повторное добавление того же ID возвращает ошибку. Для отсутствующего ID `Get`
возвращает ошибку, которую можно проверить через `errors.Is(err, sql.ErrNoRows)`.
`List` возвращает пользователей в порядке ID, для пустой таблицы — пустой срез.
Допустимые роли: `intern` и `mentor`.

Сидирование реализовано функцией `users.Seed(ctx, db)` в `internal/users/seed.go`
и запускается явно после миграций:

```sh
go run ./cmd/seed
```

Либо через Compose (сервис сам дождётся миграций):

```sh
docker compose run --rm --build seed
```

### Связь стажёра с ментором

Миграция `00001_users.sql` создаёт `mentorships` с колонками `intern_id` (PK,
FK на users) и `mentor_id` (FK на users), с каскадным удалением связей при удалении
пользователя и индексом по mentor_id. У стажёра только один ментор, у ментора
может быть несколько стажёров. Сами пользователи при удалении связи не удаляются.

`users.Mentorship` содержит InternID/MentorID без JSON-тегов. Репозиторий получил:

- `AddMentorship(ctx, link)` — добавляет связь существующего стажёра с существующим
  ментором, проверяя роли; повторное назначение стажёру возвращает ошибку.
- `ListInterns(ctx, mentorID)` — возвращает связанных стажёров в порядке ID,
  при отсутствии связей — пустой срез.

HTTP-список пользователей и demo_user сохраняют прежний формат. Отдельный API
управления назначениями в этом шаге не добавлен.

### Получение пользователей

`GET /api/users` возвращает HTTP 200 и JSON-массив всех пользователей
в порядке ID, без авторизации и пагинации:

```json
[
  {"id": "intern.backend.1", "name": "Фёдор Добронравов", "role": "intern", "team": "backend"}
]
```

Для пустой таблицы ответ — `[]`. При ошибке БД возвращается HTTP 500
с текстом `failed to list users`; подробности ошибки записываются в лог.

### Выбранный пользователь

Middleware `middleware.Middleware(userRepository)(handler)` из
`internal/users/middleware` читает cookie `demo_user`,
декодирует значение, заданное через `encodeURIComponent(user.id)`, и загружает
пользователя методом `Get`. В хендлере он доступен через
`middleware.UserFromContext(r.Context())`, возвращающий `(users.User, bool)`.

Отсутствующая или пустая cookie и неизвестный ID дают HTTP 401,
ошибка percent-кодирования — HTTP 400, ошибка репозитория — HTTP 500.
`GET /api/users` остаётся доступным без cookie для выбора пользователя.
Middleware подключён к обоим маршрутам wiki.

## Wiki и индексация

`internal/wiki.Document` содержит `ID`, `Path`, `Team`, `Title` без JSON-тегов.
Миграция `00002_wiki.sql` создаёт таблицы `documents` и `chunks`,
устанавливает расширение `vector` в схему `public`. Полный Markdown документа
читается с диска, фрагменты хранятся в `chunks`.

Общие `.md`-статьи лежат в корне `KNOWLEDGE_BASE_DIR`; для них `team` — пустая
строка. Статьи команд лежат в `<team-id>/`, вложенные каталоги поддерживаются.
Служебное описание базы знаний находится в `docs/KNOWLEDGE_BASE.md`.

Из `backend/`, после миграций:

```sh
go run ./cmd/index
```

Либо через Compose, который применит миграции, дождётся загрузки модели
Ollama и подключит `knowledge-base/` из репозитория только для чтения:

```sh
docker compose run --rm --build index
```

Команда вызывает `indexer.Indexer.Index` из `internal/wiki/indexer/indexer.go`.
Это отдельный сервис индексации. Он обходит `.md`-файлы,
вычисляет ID как SHA-256 относительного пути, берёт команду из первого каталога
и заголовок из первой строки `# ...` (при отсутствии — имя файла без `.md`).
Путь сохраняется относительно корня, с разделителем `/`.

После успешного чтения всего каталога индексатор последовательно вызывает
`Embed(ctx, chunk.Text)` для каждого фрагмента и заполняет `Chunk.Embedding`.
Только после получения всех векторов сервис передаёт документы и фрагменты
в `wiki.Repository.Sync` из `internal/wiki/repository/repository.go`.
Репозиторий одной транзакцией добавляет новые записи,
обновляет изменившиеся метаданные и удаляет записи отсутствующих файлов.
Неизменившиеся строки документов не перезаписываются. Фрагменты полностью
заменяются в той же транзакции, в том числе при изменении только текста статьи.
При переименовании файла удаляется старая запись и добавляется новая; успешно прочитанный пустой каталог очищает индекс.

При ошибке обхода, чтения файлов или получения эмбеддинга сервис не вызывает
репозиторий. Ошибка Ollama содержит ID документа и номер чанка. Ошибка БД
откатывает всю транзакцию, включая удаления. Индексация не запускается
автоматически при старте сервера.

### Фрагменты документов

`internal/wiki/chunk.go` содержит модель `Chunk` рядом с `Document`:
`DocumentID`, `Ordinal` (с нуля в пределах статьи), `Anchor`, `Text`,
`Embedding []float64`.
Связь многие-к-одному обеспечивается внешним ключом `chunks.document_id`
на `documents.id` с `ON DELETE CASCADE`. Первичный ключ — `(document_id, ordinal)`.

Колонка `embedding public.vector(768)` хранит вектор выбранной модели
`embeddinggemma:300m`. Пока вектор не получен, допускается SQL `NULL`.
`Sync` записывает переданный `Embedding`, `ListChunks` возвращает его вместе
с текстом. `nil` и пустой срез при записи означают отсутствие вектора;
при чтении SQL `NULL` возвращается как `nil`. Размерность проверяет PostgreSQL.
Внутри `vector` числа хранятся с одинарной точностью; Go-тип соответствует
результату клиента Ollama. Векторный индекс пока не создаётся.

`indexer.GetChunks(document, content)` в `internal/wiki/indexer/chunks.go`
собирает фрагменты напрямую. В начале файла заданы `chunkWordCount = 200`
и `chunkOverlapWords = 40`. Слово — последовательность непробельных символов.
Окна идут с шагом 160 слов: 1–200, 161–360 и далее; последняя часть может
быть короче. Дополнительный хвост только из перекрытия не создаётся.

Каждый раздел обрабатывается отдельно: ближайший предшествующий заголовок
задаёт `Anchor`, следующий заголовок в окно не попадает. Текущий заголовок
остаётся в тексте своего раздела и учитывается при подсчёте слов.
Текст до первого заголовка имеет пустой якорь. Пустой текст не создаёт фрагментов.
Пробелы и переносы внутри окон сохраняются; CRLF нормализуется в LF.

Парсинг заголовков построчный: `#`–`######`, отделённые пробелом или табуляцией,
с отступом не более трёх пробелов. Заголовки внутри fenced-блоков кода
с обратными кавычками или тильдами игнорируются. Подчёркнутые заголовки
`===`/`---` и сложная inline-разметка не обрабатываются.
Все вспомогательные функции находятся в `chunks.go`; Goldmark удалён.

`Anchor` содержит ID заголовка без `#` и без URL-кодирования.
Алгоритм приводит название к нижнему регистру, заменяет пробелы дефисами,
сохраняет буквы, цифры, комбинируемые знаки, `_` и `-`, удаляет остальное.
Повторы получают суффиксы `-1`, `-2` и далее с учётом уже занятых ID.
Все окна одного раздела имеют один якорь. При построении URL используйте
`encodeURIComponent(anchor)`; пустой якорь означает начало статьи.
Совместимость с `rehype-slug` рассчитана на обычные названия разделов.
Полный Markdown по HTTP по-прежнему читается из файла.

`Repository.Sync(ctx, documents, chunks)` атомарно обновляет весь индекс.
При ошибке все изменения документов и фрагментов откатываются.
`Repository.ListChunks(ctx, documentID)` возвращает фрагменты в порядке номера,
без правил доступа; для отсутствующего ID — пустой срез. Отдельного HTTP-маршрута
для фрагментов на этом шаге нет.

### Ollama

Compose запускает `ollama` и сервис `ollama-model`, который после готовности
Ollama проверяет наличие `${EMBEDDING_MODEL:-embeddinggemma:300m}` через `show`
и выполняет `pull` только при отсутствии модели. Уже скачанная модель
используется без обращения к реестру.
Модель хранится в отдельном volume `buddy-backend_ollama`.
Ollama доступна локально на `127.0.0.1:11434`, внутри Compose — `http://ollama:11434`.
Для CPU дополнительная настройка не нужна; GPU в этом шаге не настраивается.

```sh
docker compose up -d ollama ollama-model
docker compose logs -f ollama-model
```

Дождитесь успешного завершения `ollama-model` перед запросами эмбеддингов.
При локальном запуске команды Go сами не загружают `.env`-файлы; для смены
модели передайте `EMBEDDING_MODEL` также в окружение Go-процесса.

Клиент `internal/ollama.NewClient(url, model)` предоставляет
`Embed(ctx, text) ([]float64, error)` через `POST /api/embed`.
Запрос использует `truncate: false`: слишком длинный вход возвращает ошибку,
а не усечённый эмбеддинг. HTTP-таймаут — одна минута, контекст запроса учитывается.
Протокол: [Ollama Embed API](https://docs.ollama.com/api/embed).

Клиент передаётся в `indexer.NewIndexer(repository, embedder, root)` через
минимальный интерфейс `Embed(ctx, text)`. Индексация сохраняет текст и эмбеддинги
в одной транзакции после завершения всех запросов к модели. При каждом запуске
векторы пересчитываются для всех чанков; кэширование и параллельность не добавлены.

`cmd/index` использует `OLLAMA_URL` и `EMBEDDING_MODEL`. Общего минутного лимита
индексации больше нет: SIGINT/SIGTERM отменяет контекст, а каждый запрос Ollama
по-прежнему ограничен одной минутой. При переполнении контекста модели индексация
завершается ошибкой без сохранения частичного результата; чанки автоматически
не обрезаются и не переразбиваются.

### RAG

`internal/wiki/rag` предоставляет `NewRAG(repository, embedder, chunkCount)`
и `Search(ctx, query, team) ([]wiki.Chunk, error)`. При сборке потребителя
передавайте `cfg.RAGChunkCount`; команда берётся из текущего пользователя.
Поиск получает список документов и оставляет общие и документы команды.
Затем получает эмбеддинг запроса существующим клиентом Ollama и вызывает
`Repository.SearchChunks` с ID разрешённых документов и лимитом.
Репозиторий не определяет правила доступа: он ищет только в переданном наборе ID.

SQL сортирует чанки по косинусному расстоянию, затем по ID документа и номеру
чанка для стабильного порядка. Чанки без вектора исключаются. Возвращается
не более заданного количества: `DocumentID`, `Ordinal`, `Anchor`, `Text`;
векторы не загружаются в результат. Пустой доступный корпус даёт пустой срез
без запроса к модели. Пустой запрос и неположительный лимит — ошибки.
Порог схожести, полнотекстовый поиск и векторный индекс не добавлены.

### MCP-инструменты Buddy

`internal/buddy/mcp` регистрирует инструменты и открывает/закрывает in-memory
MCP-сессию. Агент создаёт отдельный обработчик и сессию на каждый запуск,
привязывая поиск к доверенной команде `user.Team`. MCP использует интерфейсы RAG
и репозитория пользователей, без прямого доступа к БД. `RAG.Search` возвращает `[]rag.Match` с документом
и чанком, используя уже загруженные метаданные документов.

- `search_documents` принимает `query`, возвращает `chunks` с полями
  `document_id`, `ordinal`, `title`, `anchor`, `text` и запоминает выдачу.
- `attach_source` принимает `document_id`, `ordinal`, выбирает ранее выданный
  чанк и возвращает только `{"attached":true}`.
- `prepare_ticket` доступен только стажёрам и принимает `title`, `description`.
  Обрезает края полей и отклоняет пустые значения. Получает назначенного ментора
  через `GetMentor` репозитория пользователей; модель не выбирает получателя.
  Возвращает `{"prepared":true}`. Без ментора вызов возвращает ошибку модели.
  Последний успешный вызов заменяет черновик; ошибка сохраняет предыдущий.
  Черновик изолирован внутри запуска, сохраняется только вместе с финальным
  сообщением. Промпт требует подтверждения пользователем в карточке;
  редактирование через чат не поддерживается.

Успешные поиски накапливаются в текущем запуске; повторная выдача чанка обновляет
сохранённые данные. Неизвестный чанк отклоняется, не меняя выбранный источник.
Последний успешный выбор заменяет предыдущий. Карточка собирается из сохранённого
результата поиска без повторного чтения документа. Векторы модели не передаются.
SDK строит схемы из именованных типов адаптера с JSON-тегами.

### Получение статей

Оба маршрута требуют cookie `demo_user`. Стажёр и ментор видят общие статьи
и статьи своей команды. Команда берётся из выбранного пользователя, а не из
параметров запроса; хендлер фильтрует список и проверяет доступ к отдельной
статье до чтения файла.

`GET /api/wiki` возвращает все доступные метаданные в порядке пути, без
пагинации. Ответ содержит `id`, `team`, `title`; путь к файлу не передаётся.
Пустой результат — `[]`:

```json
[{"id":"<sha256 пути>","team":"","title":"Руководство"}]
```

`GET /api/wiki/{id}` возвращает полный исходный Markdown статьи из файла
с `Content-Type: text/markdown; charset=utf-8`, без JSON-обёртки.
Отсутствующая, недоступная статья или исчезнувший файл дают HTTP 404.
Ошибки БД и чтения дают HTTP 500 без внутренних подробностей.
Файл читается только после проверки доступа; `os.Root` ограничивает чтение
каталогом базы знаний, в том числе при использовании символических ссылок.

HTTP-хендлер находится в `internal/wiki/handler`, методы репозитория:
`List(ctx)` и `Get(ctx, id)`. Репозиторий читает метаданные без правил доступа.
Содержимое файлов не хранится в БД.
Compose подключает каталог `knowledge-base/` серверу только для чтения.
После изменения файлов запускайте индексацию для обновления метаданных.

```sh
curl --cookie 'demo_user=intern.backend.1' http://localhost:8080/api/wiki
curl --cookie 'demo_user=intern.backend.1' http://localhost:8080/api/wiki/<id>
```

## Агент Buddy

`ollama.Client.Chat(ctx, messages, tools, emit)` обращается к `/api/chat`.
Для диалога создаётся отдельный клиент `ollama.NewChatClient(cfg.OllamaURL,
cfg.ChatModel, cfg.ChatContextLength)`; клиент индексации продолжает использовать `cfg.EmbeddingModel`.
Параметры диалога: `think: false`, `num_ctx: CHAT_CONTEXT_LENGTH` (по умолчанию 16384), `num_predict: 512`.
Без callback запрос обычный; с `emit` — потоковый. Клиент передаёт части текста
в callback и возвращает собранный ответ, включая вызовы инструментов.
Ошибка callback и отмена контекста останавливают запрос; HTTP-таймаут клиента
остаётся равным одной минуте. Поток без завершающего `done` считается ошибкой.

`agent.NewAgent(model, rag, cfg.SystemPromptFile, userRepository)` из `internal/buddy/agent` читает системный промпт из файла.
Русский промпт лежит в `prompts/buddy.md`; Compose подключает каталог к серверу.
`Agent.Generate(ctx, user, history, emit)` принимает текущего пользователя
и историю `[]buddy.Message` без системного промпта, возвращает
`buddy.Answer{Content, Source}`. Агент преобразует историю в формат Ollama
и открывает MCP-сессию через `buddy/mcp`, гарантированно закрывая её после запуска.

Каждый запрос к модели потоковый, в том числе при отсутствии callback событий.
Текст всех шагов показывается и собирается в итоговый `Content`, включая текст
перед вызовами инструментов. Ответ с вызовами добавляется в контекст вместе
с результатами MCP; ответ без вызовов завершает цикл без повторной генерации.

За запуск разрешено до шести вызовов, включая `attach_source`. Пакет сверх
оставшегося лимита отклоняется до исполнения. После шести вызовов следующий
запрос выполняется без инструментов. Неизвестный инструмент, некорректные аргументы,
ошибка MCP-вызова и результат MCP с IsError возвращаются модели как сообщение
роли tool с JSON {"error":"..."}; цикл продолжает работу. Неудачные вызовы
учитываются в общем лимите. Промпт требует сообщить пользователю, что инструмент
не может быть вызван, не повторять неудачный вызов в этом ответе и не показывать
внутренние подробности. Это инструкция модели, а не серверная гарантия формулировки.
Ошибки модели, SSE/callback, отмена запроса и превышение лимита вызовов
по-прежнему останавливают запуск. Переданная история не изменяется.
Промпт требует выбирать источник при использовании документации; без явного
`attach_source` ответ остаётся без карточки.

В Compose диалоговую модель автоматически подготавливает `ollama-chat-model`.
Имя берётся из `CHAT_MODEL`, как и у сервера; существующая модель не скачивается
заново. Для локального запуска без сервера Compose модель можно подготовить явно:

```sh
docker compose exec ollama ollama pull qwen3.5:4b
```

Подготовка модели эмбеддингов остаётся в отдельном сервисе `ollama-model`;
индексация не ждёт скачивания диалоговой модели.
Агент подключён к HTTP-серверу через сервис диалога.
Перед генерацией сервис диалога читает из БД последние `CHAT_HISTORY_LIMIT` сообщений,
включая текущий вопрос: LIMIT применяется в SQL, источники не загружаются.
Агент получает подготовленную историю без дополнительной обрезки.
Полная история остаётся в БД. Системный промпт и сообщения
вызовов/результатов инструментов текущего запуска добавляются сверх этого лимита.
Лимит числа сообщений не гарантирует, что произвольно длинный текст поместится
в окно токенов; подсчёт токенов и автоматическое сжатие не добавлены.

## Чаты и диалог

Сущности `buddy.Chat` и `buddy.Message` не зависят от протокола Ollama
и не содержат JSON-тегов. Чат хранит ID, владельца (`UserID`), название и время
создания. Сообщение хранит числовой ID, ID чата, роль (`user` / `assistant`),
текст, время создания и необязательный `Source`. Карточка содержит `DocumentID`,
`Ordinal`, `Title`, исходный `Anchor` и полный текст чанка `Quote`.
Миграция `00003_chats.sql` создаёт chats, messages и message_sources.

В `messages` хранится `attachment boolean NOT NULL DEFAULT false` — признак
наличия вложений любого вида. Реализованы источник и карточка тикета. Источник хранится
в обычных колонках `message_sources`: `message_id` (PK и FK на messages с
ON DELETE CASCADE), `document_id`, `ordinal`, `title`, `anchor`, `quote`.
Источник — снимок без внешнего ключа на документ/чанк, сохраняющийся после
переиндексации и удаления документа. Сообщение, флаг и источник записываются
одной транзакцией. При чтении истории источники сообщений с флагом загружаются
одним дополнительным запросом; без флага запрос вложений не выполняется.
Флаг остаётся деталью хранения, HTTP-формат сообщения с необязательным source
сохранён. Доменные типы без JSON-тегов, формат JSON определён HTTP-адаптером.

`message_tickets` хранит одну карточку на сообщение: `message_id` — PK/FK с
каскадным удалением, тема, описание, ID и имя получателя (снимок), nullable
уникальный FK `ticket_id`. Источник и тикет могут присутствовать одновременно.
Сообщение, флаг, источник и черновик записываются одной транзакцией; ошибка
генерации не оставляет черновик в БД. При чтении истории карточки загружаются
дополнительным запросом. Карточки задач остаются отдельным шагом.

ID чата формирует сервис, ID сообщения и время — БД.

`buddy/repository.NewRepository(db)` предоставляет `AddChat`, `GetChat`, `ListChats`,
`AddMessage`, `ListMessages`, `ListRecentMessages`, `ConfirmTicket`.
Проверка владельца при чтении выполняется сервисом; подтверждение дополнительно
ограничено владельцем, чатом и сообщением в SQL.
История возвращается по возрастанию ID сообщений; пустая история — пустой срез.
`ListMessages` читает полную историю со всеми вложениями, а `ListRecentMessages(ctx, chatID, limit)` —
только последние N сообщений без вложений.

`dialog.NewService(repository, agent, historyLimit)` из `internal/buddy/dialog` предоставляет:

- `ListChats(ctx, user)` — возвращает чаты текущего пользователя от новых к старым.
- `GetChat(ctx, user, chatID)` — проверяет владельца и возвращает чат с полной историей.
- `Send(ctx, user, chatID, text, emit)` — при пустом chatID создаёт чат
  с названием из начала сообщения; иначе проверяет владельца,
  сохраняет пользовательский текст, читает последние `historyLimit` сообщений Buddy, вызывает агента
  и сохраняет полный ответ с вложениями. После записи отправляет `source` и `ticket`
  для имеющихся вложений, затем возвращает сообщение Buddy.
- `ConfirmTicket(ctx, user, chatID, messageID, title, description)` — проверяет роль,
  поля и владельца, подтверждает карточку через репозиторий одной транзакцией.

Пользователь должен поступать из доверенного контекста. Сервис проверяет
владельца по `user.ID` и передаёт пользователя агенту; MCP остаётся внутри агента. Чужой и отсутствующий чат возвращают
`dialog.ErrNotFound`. Пустой текст отклоняется до сохранения.
При ошибке генерации или callback во время генерации сообщение пользователя
остаётся, а неполный ответ не записывается. При ошибке генерации или сохранения
событие `source` не отправляется. Ошибка записи потока после сохранения ответа
не отменяет запись в БД. Ошибка сохранения финального ответа возвращается отдельно:
полученный по потоку текст ещё не означает, что ответ сохранён.
История содержит только переписку пользователя и Buddy, без MCP-вызовов.

Сервис отклоняет параллельную отправку в один чат с `dialog.ErrBusy`.
Ограничение действует в пределах одного экземпляра сервиса; слот освобождается
при завершении или ошибке. Чтение чатов во время генерации возвращает уже сохранённые сообщения.

### Список чатов и история

Оба маршрута требуют cookie `demo_user`:

- `GET /api/chats` — JSON-массив своих чатов с `id`, `user_id`, `title`,
  `created_at`. Сортировка: `created_at DESC, id DESC`; без пагинации.
  При отсутствии чатов возвращается `[]`.
- `GET /api/chats/{id}` — те же поля чата и `messages` с полной сохранённой
  историей по возрастанию ID сообщений. Формат сообщения совпадает с SSE `done`,
  включая `source` и `ticket` (объекты или `null`). Пустая история — `[]`.

```json
{
  "id": "chat-id",
  "user_id": "intern.backend.1",
  "title": "Первый вопрос",
  "created_at": "2026-11-16T10:00:00Z",
  "messages": [
    {
      "id": 1,
      "chat_id": "chat-id",
      "role": "user",
      "content": "Как получить доступ?",
      "created_at": "2026-11-16T10:00:00Z",
      "source": null,
      "ticket": null
    }
  ]
}
```

Без выбранного пользователя — HTTP 401, чужой или отсутствующий чат — 404.
При внутренней ошибке — 500 без технических подробностей. Связь с ментором
не даёт доступа к чужой переписке. Лимит истории модели не ограничивает HTTP-историю.

### Новый чат с первым сообщением

`POST /api/chats/messages` требует cookie `demo_user` и то же тело `{ "content": "..." }`,
что и отправка в существующий чат. Сервер проверяет непустой текст до создания,
генерирует ID чата и берёт название из первых 80 Unicode-символов сообщения.
Пробельные символы в названии сворачиваются в один пробел, края обрезаются;
само сообщение сохраняется целиком, без изменения текста.

После сохранения первого вопроса сервер отправляет первое SSE-событие:

```text
event: chat
data: {"id":"new-chat-id","user_id":"intern.backend.1","title":"Как получить доступ?","created_at":"2026-11-16T10:00:00Z"}
```

Далее идут обычные события `state`, `text`, необязательные `source` и `ticket`, затем `done`
с тем же `chat_id`. Фронтенд сохраняет ID из `chat` и использует
`POST /api/chats/{id}/messages` для дальнейших сообщений. В существующем чате
событие `chat` не отправляется, название не меняется; неизвестный переданный ID
по-прежнему даёт 404, а не создаёт чат.

Ошибка генерации после `chat` приходит как SSE `error` без `done`; чат и первый
вопрос остаются доступны через GET. Ошибка записи/Flush события `chat` останавливает
генерацию, но не удаляет уже сохранённые данные. До начала SSE ошибка БД даёт 500;
создание чата и запись вопроса выполняются отдельно, поэтому при ошибке записи
первого вопроса созданный чат может остаться пустым. Повторная отправка на маршрут
без ID создаёт ещё один чат; автоматического объединения повторных запросов нет.

### Отправка сообщения и SSE-ответ

`POST /api/chats/{id}/messages` требует cookie `demo_user` и JSON:

```json
{"content":"Как получить доступ к репозиторию?"}
```

В ответ приходит `text/event-stream`. Каждый SSE-event содержит JSON в `data`:

```text
event: state
data: {"state":"thinking"}

event: state
data: {"state":"progress","progress":"search_documents"}

event: state
data: {"state":"answering"}

event: text
data: {"text":"Чтобы получить доступ…"}

event: source
data: {"document_id":"...","ordinal":2,"title":"Памятка стажёра","anchor":"экватор","quote":"..."}

event: done
data: {"id":2,"chat_id":"...","role":"assistant","content":"...","created_at":"...","source":{"document_id":"...","ordinal":2,"title":"Памятка стажёра","anchor":"экватор","quote":"..."},"ticket":null}

```

`progress` содержит фактическое имя вызываемого MCP-инструмента. Событие
отправляется перед вызовом инструмента; если модель не использует инструменты,
такого события нет. `thinking` отправляется перед каждым запросом модели,
`answering` — перед первым текстом каждого ответа модели.
`text` передаёт части текста, `source` — сохранённую карточку,
`done` — сохранённое сообщение Buddy с той же карточкой. При отсутствии выбора
`source` не отправляется, поле `source` в `done` равно `null`.
При наличии тикета после сохранения передаётся событие `ticket` с карточкой,
затем `done` с той же карточкой в поле `ticket`; без тикета это поле равно `null`.
Фронтенд строит ссылку на источник из ID документа и якоря самостоятельно.
Агент и сервис используют транспортно-независимый `buddy.Event`; хендлер
преобразует его в SSE и сразу сбрасывает каждый event через Flush.

Неверный JSON или пустой текст дают HTTP 400, отсутствие выбранного пользователя —
401, чужой или отсутствующий чат — 404, занятый чат — 409. До начала потока
внутренняя ошибка даёт HTTP 500. После начала потока ошибка передаётся событием
`error` с `{"error":"failed to generate reply"}`, без `done` и внутренних деталей.
Разрыв соединения отменяет запрос через контекст и ошибки записи/Flush.

```sh
curl -N --cookie 'demo_user=intern.backend.1' \
  -H 'Content-Type: application/json' \
  -d '{"content":"Как получить доступ к репозиторию?"}' \
  http://localhost:8080/api/chats/<chat-id>/messages
```

Для первого сообщения используйте `POST /api/chats/messages`; для продолжения — маршрут с ID.
Браузеру нужен fetch с чтением потока: EventSource не отправляет POST-тело.

## Тикеты

`internal/ticket` содержит модель `Ticket` без JSON-тегов, `repository` — PostgreSQL,
`handler` — HTTP-контракт и интерфейс репозитория. Отдельного сервисного слоя нет.
Репозиторий принимает минимальный интерфейс запросов, реализуемый `*sql.DB`
и `*sql.Tx`, чтобы вставка участвовала в транзакции подтверждения Buddy.
Созданные тикеты хранятся самостоятельно. Черновики и подтверждение принадлежат
Buddy: модель готовит карточку через `prepare_ticket`, стажёр редактирует поля
на фронтенде и подтверждает отправку. Прямой `POST /api/tickets` удалён.

Все маршруты требуют существующий `demo_user`:

- `GET /api/tickets` возвращает все доступные тикеты: стажёру — свои,
  ментору — тикеты назначенных ему стажёров. Проверка доступа выполняется в SQL
  по роли, владельцу и текущим `mentorships`, независимо от команды.
  Порядок — `created_at DESC, id DESC`, без пагинации; пустой список — `[]`.
- `GET /api/tickets/{id}` возвращает доступный тикет. Чужой и отсутствующий — 404.

Формат созданного тикета для списка и чтения:

```json
{
  "id": "random-ticket-id",
  "user_id": "intern.backend.1",
  "title": "Нет доступа",
  "description": "Нужен доступ к репозиторию",
  "created_at": "2026-11-16T10:00:00Z"
}
```

ID генерируется через `crypto/rand.Text`, время задаёт PostgreSQL; `user_id` — FK
на `users`. Без выбранного пользователя или при неизвестном ID пользователя — 401.
Внутренние ошибки — 500 без технических подробностей; детали пишутся в лог.

### Карточка и подтверждение

В SSE `ticket`, поле `ticket` события `done` и HTTP-истории используется формат:

```json
{
  "status": "draft",
  "title": "Нет доступа",
  "description": "Нужен доступ к репозиторию",
  "recipient": {"id": "mentor.backend", "name": "Сергей Дорогов"},
  "ticket_id": null
}
```

`POST /api/chats/{chatID}/messages/{messageID}/ticket/confirm` принимает
окончательные `{"title":"Нет доступа","description":"Уточнённый текст"}`.
Оба поля обязательны, обрезаются по краям и не могут состоять из пробелов.
Лимит тела — 1 МиБ; некорректный JSON, лишнее JSON-значение и пустые поля дают 400.
ID сообщения должен быть положительным целым числом.

Нужен существующий `demo_user` с ролью стажёра, свой чат и карточка в указанном
сообщении Buddy. Репозиторий блокирует строку карточки и проверяет текущее
назначение ментора. Отсутствие или смена назначения дают 409 без изменения данных.
Затем в одной транзакции создаёт тикет с окончательным текстом и связывает
его с карточкой. ID тикета генерируется сервером. Получатель остаётся снимком
из черновика; доступ ментора к созданному тикету определяется текущим назначением.

Первый успех — 201 с обновлённой карточкой: `status: "created"`, заполненный
`ticket_id`, окончательные тема и описание. Повторный запрос — 200 с тем же
результатом, новые правки игнорируются; назначение повторно не проверяется.
Параллельные подтверждения создают ровно один тикет. Состояние выводится из
наличия `ticket_id` и восстанавливается через историю после перезагрузки.
Фронтенд показывает ссылку на тикет по его ID. Отдельного сообщения Buddy
и вызова модели после подтверждения нет; правки до подтверждения хранятся
только на фронтенде.

Ошибки подтверждения: 400 — ввод, 401 — пользователь не выбран или отсутствует,
403 — роль ментора, 404 — отсутствующий или чужой чат/сообщение/карточка,
409 — назначение ментора изменилось, 500 — внутренняя ошибка без подробностей.

Интеграционные тесты пользователей, wiki, чатов и тикетов применяют миграции в отдельных временных
схемах и удаляют эти схемы после проверки. Нужна тестовая PostgreSQL-база
с pgvector и правом создания схем. Расширение `vector` должно быть установлено
в `public` до параллельного запуска тестов (например, командой migrate);
без `TEST_DATABASE_URL` эти тесты пропускаются:

```sh
TEST_DATABASE_URL=postgres://buddy:buddy@localhost:5432/buddy_test?sslmode=disable go test -race -count=1 ./...
```
