# Backend

Минимальный Go-бэкенд. Конфигурация читается из окружения через cleanenv:

| Переменная | Значение |
| --- | --- |
| `ADDR` | Адрес HTTP-сервера, по умолчанию `:8080` |
| `DATABASE_URL` | Обязательный URL PostgreSQL |
| `KNOWLEDGE_BASE_DIR` | Путь к базе знаний, по умолчанию `../knowledge-base` |
| `OLLAMA_URL` | Адрес Ollama, по умолчанию `http://localhost:11434` |
| `EMBEDDING_MODEL` | Модель эмбеддингов, по умолчанию `embeddinggemma:300m` |

## Docker Compose

Из каталога `backend/`:

```sh
docker compose up --build -d
docker compose logs server migrate
```

Compose ждёт готовности PostgreSQL, применяет миграции отдельным сервисом
`migrate` и запускает сервер на порту 8080. Список пользователей доступен
по `GET /api/users`. База доступна локально на `127.0.0.1:5432`.
Для нового бэкенда используется отдельный volume `buddy-backend_postgres`.
Порт 8080 должен быть свободен от прежнего бэкенда.

Повторно применить миграции:

```sh
docker compose run --rm --build migrate
```

На текущем этапе разработки при изменении миграций нужно сбрасывать БД,
удаляя только volume PostgreSQL, и затем заново применять миграции и сид
(volume Ollama с загруженной моделью сохраняем):

```sh
docker compose down
docker volume rm buddy-backend_postgres
docker compose up --build -d
docker compose run --rm --build seed
docker compose run --rm --build index
```

## Локальный запуск

Из каталога `backend/` (нужен Go 1.27):

```sh
docker compose up -d postgres
set -a
. ./.env.example
set +a
go run ./cmd/migrate
go run ./cmd/server
```

Программа сама не загружает `.env`-файлы. `.env.example` содержит только локальные
значения; Compose использует `POSTGRES_PASSWORD` из окружения или `.env`
(по умолчанию `buddy`). При смене пароля нужно также обновить локальный `DATABASE_URL`.

Миграции лежат в `migrations/` и выполняются goose по порядку. Команду
`cmd/migrate` нужно запускать из `backend/`. Первая миграция
`00001_users.sql` создаёт таблицу `users`.

## Пользователи и сидирование

Пакет `internal/users` содержит сущность `User` с полями `ID`, `Name`, `Role`,
`Team`. HTTP-хендлер находится в `internal/users/handler/handler.go`.
PostgreSQL-репозиторий `users.Repository` находится
в `internal/users/repository/repository.go`: `Add`, `Get`, `List`. ID задаёт вызывающий код;
повторное добавление того же ID возвращает ошибку. Для отсутствующего ID `Get`
возвращает ошибку, которую можно проверить через `errors.Is(err, sql.ErrNoRows)`.
`List` возвращает пользователей в порядке ID, для пустой таблицы — пустой срез.
Допустимые роли: `intern` и `mentor`.

Сидирование реализовано функцией `users.Seed(ctx, db)` в `internal/users/seed.go`
и запускается явно после миграций:

```sh
go run ./cmd/seed
```

Либо через Compose (сервис сам дождётся миграций):

```sh
docker compose run --rm --build seed
```

### Получение пользователей

`GET /api/users` возвращает HTTP 200 и JSON-массив всех пользователей
в порядке ID, без авторизации и пагинации:

```json
[
  {"id": "intern.backend.1", "name": "Фёдор Добронравов", "role": "intern", "team": "backend"}
]
```

Для пустой таблицы ответ — `[]`. При ошибке БД возвращается HTTP 500
с текстом `failed to list users`; подробности ошибки записываются в лог.

### Выбранный пользователь

Middleware `middleware.Middleware(userRepository)(handler)` из
`internal/users/middleware` читает cookie `demo_user`,
декодирует значение, заданное через `encodeURIComponent(user.id)`, и загружает
пользователя методом `Get`. В хендлере он доступен через
`middleware.UserFromContext(r.Context())`, возвращающий `(users.User, bool)`.

Отсутствующая или пустая cookie и неизвестный ID дают HTTP 401,
ошибка percent-кодирования — HTTP 400, ошибка репозитория — HTTP 500.
`GET /api/users` остаётся доступным без cookie для выбора пользователя.
Middleware подключён к обоим маршрутам wiki.

## Wiki и индексация

`internal/wiki.Document` содержит `ID`, `Path`, `Team`, `Title` без JSON-тегов.
Миграция `00002_wiki.sql` создаёт таблицу `documents`. Полный Markdown документа
читается с диска. Фрагменты хранятся отдельно в таблице `chunks`
(миграция `00003_chunks.sql`); эмбеддинги пока не сохраняются.

Общие `.md`-статьи лежат в корне `KNOWLEDGE_BASE_DIR`; для них `team` — пустая
строка. Статьи команд лежат в `<team-id>/`, вложенные каталоги поддерживаются.
Служебное описание базы знаний находится в `docs/KNOWLEDGE_BASE.md`.

Из `backend/`, после миграций:

```sh
go run ./cmd/index
```

Либо через Compose, который применит миграции и подключит `knowledge-base/`
из репозитория только для чтения:

```sh
docker compose run --rm --build index
```

Команда вызывает `indexer.Indexer.Index` из `internal/wiki/indexer/indexer.go`.
Это отдельный сервис индексации. Он обходит `.md`-файлы,
вычисляет ID как SHA-256 относительного пути, берёт команду из первого каталога
и заголовок из первой строки `# ...` (при отсутствии — имя файла без `.md`).
Путь сохраняется относительно корня, с разделителем `/`.

После успешного чтения всего каталога сервис передаёт списки документов и фрагментов
в `wiki.Repository.Sync` из `internal/wiki/repository/repository.go`.
Репозиторий одной транзакцией добавляет новые записи,
обновляет изменившиеся метаданные и удаляет записи отсутствующих файлов.
Неизменившиеся строки документов не перезаписываются. Фрагменты полностью
заменяются в той же транзакции, в том числе при изменении только текста статьи.
При переименовании файла удаляется старая запись и добавляется новая; успешно прочитанный пустой каталог очищает индекс.

При ошибке обхода или чтения файлов сервис не вызывает репозиторий. Ошибка БД
откатывает всю транзакцию, включая удаления. Индексация не запускается
автоматически при старте сервера.

### Фрагменты документов

`internal/wiki/chunk.go` содержит модель `Chunk` рядом с `Document`:
`DocumentID`, `Ordinal` (с нуля в пределах статьи), `Anchor`, `Text`.
Связь многие-к-одному обеспечивается внешним ключом `chunks.document_id`
на `documents.id` с `ON DELETE CASCADE`. Первичный ключ — `(document_id, ordinal)`.

`indexer.SplitChunks` разбивает текст по CommonMark-заголовкам (включая
подчёркнутые `===`/`---`), игнорируя заголовки внутри блоков кода. Длинные разделы делятся на части
до 1200 Unicode-символов с предпочтением границ абзацев, затем пробелов.
Перекрытия между фрагментами нет. Пустой текст не создаёт фрагментов.
Это текст для поиска; полный Markdown по HTTP по-прежнему читается из файла.

`Anchor` содержит ID заголовка без `#` и без URL-кодирования.
Простой алгоритм приводит текст к нижнему регистру, заменяет пробелы дефисами,
сохраняет буквы, цифры, комбинируемые знаки, `_` и `-`, удаляет остальную
пунктуацию. Повторы получают суффиксы `-1`, `-2` и далее с учётом уже занятых ID.
Все части длинного раздела имеют один якорь. До первого заголовка якорь пустой.
При построении URL используйте `encodeURIComponent(anchor)`; пустой якорь
означает переход к началу статьи.

Распознавание заголовков выполняет Goldmark. Алгоритм рассчитан на обычные
названия на русском и английском; полное совпадение с `rehype-slug` для сложной
разметки и редких Unicode-символов не требуется. JS-эталоны, генераторы таблиц
и зависимость от Node.js для тестов удалены.

`Repository.Sync(ctx, documents, chunks)` атомарно обновляет весь индекс.
При ошибке все изменения документов и фрагментов откатываются.
`Repository.ListChunks(ctx, documentID)` возвращает фрагменты в порядке номера,
без правил доступа; для отсутствующего ID — пустой срез. Отдельного HTTP-маршрута
для фрагментов на этом шаге нет.

### Ollama

Compose запускает `ollama` и сервис `ollama-model`, который после готовности
Ollama загружает `${EMBEDDING_MODEL:-embeddinggemma:300m}` командой `pull`.
Модель хранится в отдельном volume `buddy-backend_ollama`.
Ollama доступна локально на `127.0.0.1:11434`, внутри Compose — `http://ollama:11434`.
Для CPU дополнительная настройка не нужна; GPU в этом шаге не настраивается.

```sh
docker compose up -d ollama ollama-model
docker compose logs -f ollama-model
```

Дождитесь успешного завершения `ollama-model` перед запросами эмбеддингов.
При локальном запуске команды Go сами не загружают `.env`-файлы; для смены
модели передайте `EMBEDDING_MODEL` также в окружение Go-процесса.

Клиент `internal/ollama.NewClient(url, model)` предоставляет
`Embed(ctx, text) ([]float64, error)` через `POST /api/embed`.
Запрос использует `truncate: false`: слишком длинный вход возвращает ошибку,
а не усечённый эмбеддинг. HTTP-таймаут — одна минута, контекст запроса учитывается.
Протокол: [Ollama Embed API](https://docs.ollama.com/api/embed).

Клиент пока не подключён к индексатору: на этом шаге сохраняются текстовые
фрагменты. Генерация и хранение эмбеддингов, векторный поиск и интеграция
с агентом — следующие отдельные шаги.

### Получение статей

Оба маршрута требуют cookie `demo_user`. Стажёр и ментор видят общие статьи
и статьи своей команды. Команда берётся из выбранного пользователя, а не из
параметров запроса; хендлер фильтрует список и проверяет доступ к отдельной
статье до чтения файла.

`GET /api/wiki` возвращает все доступные метаданные в порядке пути, без
пагинации. Ответ содержит `id`, `team`, `title`; путь к файлу не передаётся.
Пустой результат — `[]`:

```json
[{"id":"<sha256 пути>","team":"","title":"Руководство"}]
```

`GET /api/wiki/{id}` возвращает полный исходный Markdown статьи из файла
с `Content-Type: text/markdown; charset=utf-8`, без JSON-обёртки.
Отсутствующая, недоступная статья или исчезнувший файл дают HTTP 404.
Ошибки БД и чтения дают HTTP 500 без внутренних подробностей.
Файл читается только после проверки доступа; `os.Root` ограничивает чтение
каталогом базы знаний, в том числе при использовании символических ссылок.

HTTP-хендлер находится в `internal/wiki/handler`, методы репозитория:
`List(ctx)` и `Get(ctx, id)`. Репозиторий читает метаданные без правил доступа.
Содержимое файлов не хранится в БД.
Compose подключает каталог `knowledge-base/` серверу только для чтения.
После изменения файлов запускайте индексацию для обновления метаданных.

```sh
curl --cookie 'demo_user=intern.backend.1' http://localhost:8080/api/wiki
curl --cookie 'demo_user=intern.backend.1' http://localhost:8080/api/wiki/<id>
```

## Проверки

```sh
go test ./...
go vet ./...
go build ./...
golangci-lint fmt --diff
golangci-lint run ./...
docker compose config --quiet
```

Интеграционные тесты пользователей и wiki применяют миграции в отдельных временных
схемах и удаляют эти схемы после проверки. Нужна тестовая PostgreSQL-база
с правом создания схем; без `TEST_DATABASE_URL` эти тесты пропускаются:

```sh
TEST_DATABASE_URL=postgres://buddy:buddy@localhost:5432/buddy_test?sslmode=disable go test -race -count=1 ./...
```
