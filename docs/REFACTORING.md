# Рефакторинг Buddy AI вместе с пользователем

## Цель и исходное состояние

Пошагово разобрать каждую фичу бэкенда, установить понятные границы ответственности,
размещение типов, интерфейсов и функций. Одновременно упростить функциональность
до требований ниже. Пользователь руководит работой вплоть до отдельных функций.
Сокращение числа строк не является самостоятельной целью.

Текущая реализация перенесена в `backend-ai/`. Её Go-модуль и корень импортов —
`backend-ai`, Compose-проект — `backend-ai`, бинарник — `backend-ai-server`.
Предметные имена пакетов пока сохранены: их организация будет обсуждаться по фичам.
Прежний код остаётся рабочим образцом для изучения и сравнения.
В новом `backend/` создана минимальная основа запуска: конфигурация, HTTP-сервер,
подключение PostgreSQL, команда миграций и Docker Compose. Структуру прикладного
кода определяем вместе с пользователем при разборе фич.

Эта инструкция фиксирует новые продуктовые требования. `SDD.md`, OpenAPI и README
в `backend-ai/` описывают прежнюю реализацию и не задают обязательный функционал
нового бэкенда. При расхождениях следовать последним явным указаниям пользователя.

## Что должно уметь приложение

Фронтенд — одно приложение Buddy AI. Здесь описаны возможности, которые должен
обслуживать бэкенд; реализация фронтенда не является частью текущего шага.

| Возможность | Требуемое поведение |
| --- | --- |
| Выбор пользователя | Окно выбора пользователя вместо реальной авторизации. Роли: стажёр и ментор. |
| Чаты | Стажёр создаёт несколько чатов и общается с агентом. |
| Поиск документов | Агент использует RAG, к ответу прилагается ссылка на источник. |
| Создание задачи | Инструмент создаёт черновик от лица стажёра. Стажёр подтверждает его кнопкой в чате; только затем создаётся задача. |
| Завершение задачи | Требуется явный клик стажёра. Текстовый запрос и решение модели не заменяют клик. |
| Карточки задач | Задачи показываются карточками прямо в чате. |
| Создание тикета | Инструмент создаёт черновик от лица стажёра. Стажёр подтверждает его кнопкой в чате; отдельного интерфейса создания нет. |
| Прогресс агента | Стажёр видит прогресс вызовов инструментов и поток текста ответа. |
| Дашборд стажёра | Отображение его заданий. |
| Дашборд ментора | Выбор стажёра и просмотр его заданий. |
| Вики | Для демо — весь список доступных документов без пагинации и отдельные страницы статей. Доступны общие статьи и статьи команды пользователя. Markdown рендерит фронтенд. |
| Карточки тикетов | Черновик с явным подтверждением стажёром; после создания та же карточка показывает результат и ссылку на тикет. |
| Просмотр тикетов | Стажёр видит созданные им тикеты, ментор — тикеты его стажёров. |

Если возможность не описана, считать её отсутствующей. Не добавлять по аналогии
редактирование, удаление, дополнительные кнопки, экраны или операции. Например,
кнопка завершения задачи на дашборде не установлена требованиями.
Не переносить автоматически технические механизмы старого бэкенда: необходимость
каждого определяется на соответствующем шаге. Подтверждение создания и явный клик
для завершения должны обеспечиваться сервером, а не только системным промптом.

Системный промпт остаётся отдельным файлом, путь передаётся через ENV; текст промпта
на русском и требует отвечать по-русски.

## Как работать на каждом шаге

1. Пользователь выбирает фичу, участок кода или конкретную функцию. Агент сначала
   читает относящийся к ней код и объясняет текущее поведение и зависимости.
2. Обсудить желаемое поведение и структуру выбранного участка: что оставить,
   удалить или изменить; кто отвечает за данные и операции; какие интерфейсы
   действительно нужны. Не выбирать архитектуру всего проекта за пользователя.
3. Зафиксировать принятое решение в этой инструкции. Неустановленные детали
   не превращать в скрытые требования. Вопросы задавать только о решениях,
   необходимых для текущего шага и не выводимых из кода или разговора.
4. Когда пользователь поручает реализацию, выполнить её в указанном объёме.
   Уже порученное изменение не требует повторного подтверждения. Команда изменить
   одну функцию не разрешает попутную переработку остальных подсистем.
5. Проверить выбранный сценарий. Для изменения поведения нужны содержательные
   тесты; при переносе кода достаточно соответствующих существующих проверок.
   При изменении API, схемы данных или запуска обновить относящуюся к шагу документацию.
6. Сообщить результат и проверки, записать завершённый шаг и открытые вопросы.
   Следующую фичу выбирает пользователь.

Каждый десятый шаг резюмировать последние 10 завершённых шагов, включая текущий,
в одном разделе `Шаги <начало>–<конец>`: `Шаги 1–10`, `Шаги 11–20` и т. д.
Заменять подробные записи этой десятки кратким резюме: результат, действующие
решения, существенные ограничения, проверки и оставшиеся вопросы. Промежуточные
обсуждения включать в резюме; отменённые решения не оставлять как действующие.
Шаги после последней полной десятки пока сохранять отдельными записями.

Если пользователь просит только обсуждение, ограничиться чтением и обсуждением.
Не создавать код, заглушки или каркас. Не запускать параллельную самостоятельную
переработку других фич.

## Что устанавливать при разборе структуры

- Какая ответственность у пакета и какие зависимости ему нужны.
- Где находятся модели данных, входные и выходные типы, обработчики, бизнес-правила
  и работа с хранилищем. Не назначать универсальное дерево каталогов заранее.
- Структуры запросов и ответов объявлять именованными типами после структуры
  `Handler` или `Client`, но перед методами в соответствующем файле,
  а не внутри методов.
- Кому нужен каждый интерфейс и какие методы этот потребитель вызывает.
  Не складывать интерфейсы в `model.go` только ради общего места хранения.
- Какие функции образуют один сценарий и должны читаться рядом. Не дробить
  сценарий на файлы по одной функции без практической причины.
- Какие проверки относятся к бизнес-правилам, а какие — к HTTP или инструменту.
  Правила доступа и изменения данных не должны зависеть от поведения модели.
- Какие части старого поведения действительно нужны. Совместимость старого API
  и БД не считать требованием нового бэкенда без указания пользователя;
  на текущем этапе данные БД сохранять не требуется. При изменении или
  перенумерации миграций нужно сбрасывать volume БД нового `backend/`
  (`docker compose down`, затем `docker volume rm buddy-backend_postgres`
  из `backend/`), затем применять миграции и сид заново. Это разрешено пользователем и не требует повторного согласования.
  Данное разрешение относится к БД, а не к другим volumes, например Ollama.

## Проверка прежнего бэкенда после переноса

Из `backend-ai/`:

```sh
env -u TEST_DATABASE_URL go test -race -count=1 ./...
go vet ./...
golangci-lint fmt --diff
golangci-lint run ./...
go build -o /tmp/backend-ai-server ./cmd/server
docker compose -f deploy/compose.yaml --env-file deploy/.env.example config --quiet
```

Проверки с БД требуют отдельного `TEST_DATABASE_URL`; без него они пропускаются.
Compose создаёт контейнеры `backend-ai-app-1`, `backend-ai-postgres-1` и
`backend-ai-ollama-1`. По умолчанию имена существующих volumes сохранены:
`ai-buddy_postgres` и `ai-buddy_ollama`; их можно переопределить через
`POSTGRES_VOLUME_NAME` и `OLLAMA_VOLUME_NAME`.
Перенос исходников сам по себе не переименовывает уже запущенные контейнеры.
Прежний и новый Compose-проекты не следует запускать одновременно с общей БД.

## Состояние работы

Прежняя реализация находится в `backend-ai/`. В новом `backend/` работают запуск,
миграции, пользователи и demo_user, чтение wiki, индексация с эмбеддингами, RAG,
агент с MCP, хранение диалога и SSE с карточкой источника. Текущие команды запуска
и контракты подробно описаны в [backend/README.md](../backend/README.md).

Открыто: HTTP создания/списка чатов и истории;
бюджет контекста; подготовка диалоговой модели в Compose; фронтенд карточки;
задачи и тикеты с подтверждениями, дашборды и инструменты ticket/tracker.
В старом коде `complete_task` допускает завершение по текстовой просьбе — исправлять
только по отдельной команде пользователя. Следующий участок выбирает пользователь.

### Шаги 1–10: основа backend, пользователи и индекс wiki

- Создан Go-модуль `backend`, конфиг через cleanenv (`ADDR=:8080`, обязательная
  `DATABASE_URL`), HTTP-сервер и PostgreSQL через database/sql + pgx. Подключение
  проверяется при старте сервера; SIGINT/SIGTERM завершают HTTP-запросы.
  Отдельная команда миграций использует goose. Compose-проект `buddy-backend`
  и его volume изолированы от прежнего бэкенда; настройки линтера упрощены.
- `users.User` содержит ID, Name, Role, Team без JSON-тегов; роли intern/mentor.
  `users/repository.Repository` предоставляет Add/Get/List. ID задаёт вызывающий
  код, Add не перезаписывает дубликат, Get сохраняет sql.ErrNoRows, List возвращает
  записи по ID и пустой срез вместо nil. SQL расположен рядом с вызовами.
- `00001_users.sql` заменила пустую init-миграцию. Сохранены PK, NOT NULL и
  проверка ролей; избыточные проверки пустых строк и повторный Ping мигратора
  удалены. Разрешён сброс только БД нового бэкенда по правилу выше.
- Явная команда seed транзакционно добавляет шесть пользователей: по два стажёра
  и одному ментору backend/platform, с именами из «6 кадров». Существующие ID
  пропускаются без перезаписи; явная связь стажёр–ментор добавлена в шаге 39.
  Публичный `GET /api/users` возвращает id/name/role/team, при ошибке — 500
  без внутренних подробностей. JSON-формат определён HTTP-адаптером.
- `wiki.Document`: ID, Path, Team, Title без JSON-тегов; `00002_wiki.sql`
  создаёт documents с уникальным путём. `KNOWLEDGE_BASE_DIR=../knowledge-base`.
  Общие статьи перенесены из common в корень, командные — в каталоги команд;
  служебное описание находится в docs/KNOWLEDGE_BASE.md.
- Метаданные: относительный путь с `/`, ID — SHA-256 пути, команда — первый
  каталог либо пустая строка, title — первая строка `# ...` либо имя файла.
  `wiki/indexer.Indexer` читает весь каталог; `wiki/repository.Repository.Sync`
  одной транзакцией добавляет/обновляет документы и удаляет отсутствующие.
  Переименование меняет ID, пустой каталог очищает индекс, ошибка чтения/БД
  сохраняет прежний индекс. Команда index запускается явно.
- Проверки на соответствующих шагах: PostgreSQL, тесты с -race, vet, сборка,
  форматирование, линтер, Compose и Docker-сборка; проверены миграции, сид,
  HTTP, повторная синхронизация и откат. На реальной базе проиндексировано
  35 статей без дублей. Открытые тогда чтение wiki и RAG реализованы ниже.

### Шаги 11–20: выбор пользователя, чтение wiki и текстовые чанки

- Исправлены импорты после пользовательских перемещений без изменения структуры.
  Сид оформлен как `users.Seed(ctx, db)`, хендлер и middleware находятся
  в users/handler и users/middleware.
- Middleware читает cookie demo_user, декодирует ID через PathUnescape
  (знак `+` сохраняется), загружает User и помещает его в контекст.
  `middleware.UserFromContext` получает пользователя; нет/пустая cookie или
  неизвестный ID — 401, неверное кодирование — 400, ошибка БД — 500.
- `GET /api/wiki` возвращает все доступные id/team/title в порядке пути, без
  пагинации, limit/offset/total и пути файла. `GET /api/wiki/{id}` возвращает
  полный исходный Markdown с text/markdown; charset=utf-8, без JSON-обёртки.
  Оба маршрута защищены middleware. Обе роли видят общие статьи и статьи своей
  команды; чужой/отсутствующий документ или исчезнувший файл — 404.
- Правила доступа находятся в wiki/handler, до чтения файла; репозиторий
  List/Get читает метаданные без команды и правил доступа. Файлы открываются
  через os.Root, ограничивающий доступ корнем базы знаний, включая symlink.
  Ошибки БД/чтения дают 500 без подробностей. Каталог в Compose — только чтение.
- `ollama.Client.Embed` использует POST /api/embed, truncate:false, контекст
  и минутный HTTP-таймаут; проверяет статус, JSON и один непустой вектор.
  Дефолты: `OLLAMA_URL=http://localhost:11434`,
  `EMBEDDING_MODEL=embeddinggemma:300m`. Compose добавлены Ollama, healthcheck,
  сервис подготовки модели и отдельный volume, сохраняемый при сбросе БД.
- `wiki.Chunk` и таблица chunks (теперь в `00002_wiki.sql`): DocumentID, Ordinal с нуля, Anchor, Text;
  PK (document_id, ordinal), FK на документ с каскадным удалением. Sync сохраняет
  метаданные и полную замену чанков одной транзакцией; ListChunks читает по номеру.
- Anchor заменил Section: хранится без `#` и URL-кодирования, общий для частей
  раздела, пустой до первого заголовка. Точное совпадение с rehype-slug отменено:
  достаточно обычных русских/английских названий. Используются ToLower,
  Unicode-категории букв/цифр/комбинируемых знаков, дефис и подчёркивание;
  пробелы заменяются дефисами, прочее удаляется, коллизии получают суффиксы.
  JS-эталоны и специальные Unicode-таблицы удалены. Окончательная нарезка — ниже.
- Проверки: тесты с PostgreSQL и -race, vet, сборка, форматирование, линтер,
  Compose/Docker; доступ обеих ролей, ошибки cookie/БД/файлов, защита корня,
  чанки, якоря, каскадное удаление и атомарность Sync. Ollama на этом этапе
  проверялась HTTP-заглушкой; реальная индексация с моделью выполнена позже.

### Шаги 21–30: нарезка 200/40, векторы, RAG и основа агента

- Уточнён порядок типов запросов/ответов: после Handler/Client, перед методами
  (правило закреплено выше). Дополнительные слои не вводились.
- `indexer.GetChunks(document, content)` объединяет парсинг и нарезку:
  окна по 200 слов с перекрытием 40, шаг 160, отдельно внутри каждого раздела.
  Заголовок входит в текст, короткий последний чанк сохраняется, хвост только
  из перекрытия не добавляется. Слова — непробельные последовательности;
  форматирование сохраняется, CRLF нормализуется в LF, пустой текст без чанков.
- Простой построчный парсер распознаёт `#`–`######` с пробелом/табуляцией и
  отступом до трёх пробелов, учитывает fenced code blocks. Подчёркнутые заголовки
  и сложная inline-разметка не разбираются; Goldmark удалён. Якоря остаются
  простыми, как согласовано в предыдущей десятке.
- У Chunk добавлен Embedding []float64; chunks.embedding — nullable
  public.vector(768), расширение pgvector в public. Compose использует
  pgvector/pgvector:pg16. Sync/ListChunks сохраняют/читают вектор, nil/пустой
  срез — SQL NULL; размерность проверяет БД, точность одинарная. Индекса нет.
- Индексатор последовательно получает векторы всех чанков перед Sync.
  При ошибке чтения/модели или отмене прежний индекс сохраняется; пустой каталог
  очищает индекс без вызова модели. Кэша и параллельности нет, векторы считаются
  заново. cmd/index отменяется по SIGINT/SIGTERM; таймаут запроса — в клиенте.
  ollama-model сначала делает show, затем pull только при отсутствии модели.
- `wiki/rag.Search(ctx, query, team)` выбирает общие/командные документы,

### Шаг 34: карточка источника и единый потоковый цикл MCP

- По утверждённому плану MCP перенесён в buddy/mcp: регистрация инструментов,
  открытие/закрытие in-memory-сессии. Агент создаёт отдельный обработчик на запуск
  и гарантированно закрывает сессию. MCP зависит от интерфейса RAG, без доступа к БД.
- `RAG.Search` возвращает []rag.Match{Document, Chunk} с уже загруженными
  метаданными. search_documents возвращает также title, накапливает успешные
  выдачи текущего запуска; повторная выдача обновляет чанк. attach_source
  (document_id, ordinal) выбирает только ранее выданный чанк и возвращает
  {"attached":true}. Последний успешный выбор заменяет предыдущий; ошибка
  выбора источник не меняет. Карточка берётся из выдачи без повторного чтения.
- `Agent.Generate(ctx, user, history, emit)` принимает []buddy.Message и возвращает
  buddy.Answer{Content, Source}; преобразование в Ollama — в агенте. Каждый запрос
  потоковый, ответ без вызовов завершает цикл без повторной генерации. Весь
  показанный текст, включая текст перед инструментами, входит в Content.
  Лимит шесть включает attach_source; пакет сверх остатка не исполняется,
  после исчерпания следующий запрос — без инструментов. thinking — перед каждым
  запросом, answering — перед первым текстом каждого ответа, progress — перед MCP.
- buddy.Source: DocumentID, Ordinal, Title из Document.Title, исходный Anchor
  и полный текст чанка Quote. Необязательный Source добавлен у Message/Event
  и Answer. Доменные типы без JSON-тегов; форматы — у адаптеров. Первоначальное
  хранение карточки в JSONB заменено отдельной таблицей в шаге 36.
  Переиндексация и удаление документа не меняют старые сообщения.
- dialog не импортирует Ollama/MCP. После записи ответа отправляет source,
  хендлер затем — done с той же карточкой. Без выбора события source нет,
  в done — null. При ошибке генерации/сохранения source не отправляется;
  ошибка потока после записи не удаляет ответ. Промпт требует явного выбора
  источника, автоматического выбора нет. Фронтенд строит URL из ID и Anchor;
  отдельное название раздела и изменение индексации не нужны.
- Полный прогон с отдельным PostgreSQL/pgvector и -race, vet, сборка,
  форматирование, линтер (0 замечаний) и diff-check прошли: накопление/обновление
  и изоляция выдачи, выбор/замена источника, весь потоковый текст, лимит/отмена,
  SSE и совпадение карточек, ошибки записи/потока, SQL NULL, атомарность и снимок
  после переиндексации/удаления. README обновлён. Основная БД не менялась,
