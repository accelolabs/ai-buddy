# SDD AI Buddy

## 1. Развертывание

Buddy, Wiki, Tracker и Ticket - отдельные Go-сервисы. Authentik отвечает за вход. У каждого компонента свой Compose-файл, собственная PostgreSQL БД и учетные данные: authentik-db, buddy-db, wiki-db, tracker-db и ticket-db. Для взаимодействия контейнеры подключаются к общей сети Compose. Межсервисные операции проходят через API владельца данных.

Все четыре Go-сервиса используют net/http, cleanenv и goose. Миграции и повторяемое сидирование подготавливают демо-пользователей, команды, назначения, задачи, документы и тикеты. Повторное сидирование сохраняет изменения, сделанные в демо.

## 2. Вход и права

- Authentik хранит пользователей, роль стажера или наставника и команду. Каждый Go-сервис имеет свой OIDC-клиент и свою серверную сессию. При входе сервис сохраняет данные пользователя до следующего входа. Общий идентификатор берется из отдельного OIDC claim с ID пользователя Authentik.
- Чат Buddy доступен только стажеру. Вход наставника в Buddy заканчивается отказом в доступе к чату. Переключатель на макете трактуем как навигацию к дашборду или указание доступного раздела по роли. Права определяет сервер.
- Для REST-вызовов Buddy берет ID стажера из своей сессии и передает его с API-ключом. Wiki, Tracker и Ticket принимают такой ID только с действительным ключом Buddy и проверяют доступ к ресурсу. Ключи остаются на серверах.
- Ticket получает назначение через Tracker. Его отдельный ключ разрешает только поиск наставника по ID стажера.
- Wiki узнает команду пользователя из Authentik для межсервисного поиска. Доступ к странице Wiki проверяет по собственной сессии. При недоступности Authentik поиск по команде возвращает ошибку.

## 3. Buddy и чат

Сайдбар показывает историю диалогов и кнопку нового чата. Стажер открывает любой свой диалог. Стартовый экран предлагает документы команды, защиту данных, прогресс и памятку о практике. Быстрые действия запускают те же сценарии, что текстовый запрос или команда /progress.

Buddy хранит диалоги, сообщения и состояние текущего ответа. Один MCP-сервер в Buddy предоставляет инструменты агента и вызывает REST API Wiki, Tracker и Ticket. Бэкенд подставляет личность пользователя и ключи из доверенного контекста. Модель получает только параметры операции.

### Ответ и SSE

- POST сообщения сохраняет его и возвращает ID запуска. GET SSE с этим ID проверяет владельца диалога и передает этап работы, части текста, карточки и ссылки. Поток заканчивается событием завершения или ошибки.
- Этапы на экране соответствуют фактической работе: разбор запроса, поиск или вызов сервиса, формирование ответа. Части текста дописываются в одно сообщение. Карточки передаются целиком.
- После обрыва SSE генерация продолжается. При переподключении Buddy передает накопленный ответ и карточки, затем новые события. Номера событий позволяют избежать повторной вставки текста. Порядок событий сохраняется и при быстром завершении до первого GET.
- При сбое MCP Buddy отправляет ошибку через SSE и предлагает повтор вручную. Для подтвержденной операции создания повтор использует тот же ключ идемпотентности.

## 4. Tracker

Tracker хранит задачи стажера и фиксированные назначения. У стажера один наставник или назначение отсутствует. У наставника может быть несколько стажеров.

| Операция | Вход | Результат |
| --- | --- | --- |
| `get_progress` | ID стажера из сессии или доверенного вызова | Все задачи со статусами и сроками, счетчик выполненных, следующий шаг |
| `create_task` | Название и дедлайн обязательны, описание опционально | Сохраненная задача с ID |
| `complete_task` | ID своей задачи | Сохраненное состояние задачи. Повтор возвращает успех с тем же состоянием |
| Поиск наставника | ID стажера и ключ Ticket | ID и данные назначенного наставника либо явное отсутствие назначения |

Стажер создает и завершает свои задачи через Tracker или Buddy. Редактирование задач вне объема версии. Дедлайн передается как YYYY-MM-DD, хранится как date. Сегодняшний дедлайн считается просроченным со следующего дня по часовому поясу приложения.

В чате запрос на создание задачи открывает черновик с кнопкой подтверждения. Явная просьба завершить однозначно распознанную задачу сразу вызывает Tracker. При совпадении нескольких задач Buddy просит уточнить название текстом.

Карточка прогресса показывает роль стажера в команде, наставника, дату старта, счетчик и шкалу выполнения. Следующий шаг - первая просроченная незавершенная задача по порядку списка, иначе задача с ближайшим сроком. Равные сроки разрешаются порядком списка. Когда все задачи выполнены, карточка сохраняет список и показывает соответствующее сообщение. Кнопка завершения меняет карточку после ответа Tracker. При сбое прежний статус сохраняется и появляется "Повторить".

Дашборд "Мои стажеры" находится в Tracker. Наставник выбирает закрепленного стажера и видит тот же список, сроки, счетчик, цели и ожидания. "Обновить" перечитывает данные. Дашборд доступен для чтения.

## 5. Ticket

| Операция | Вход | Результат |
| --- | --- | --- |
| `create_ticket` | Вопрос, описание, ключ идемпотентности | ID и сохраненный тикет |
| `list_tickets` | Личность стажера | Все отправленные им тикеты |
| Входящие наставника | Личность из сессии Ticket | Тикеты, где пользователь указан получателем |

Тикет хранит отправителя, получателя, вопрос и описание. Оба текстовых поля обязательны. Получателя определяет Ticket через Tracker. Если назначения нет, операция отклоняется с сообщением "Ментор не назначен". При сбое Tracker Ticket сообщает об ошибке и сохранять заявку можно после успешного определения получателя.

Если в базе знаний нет ответа, Buddy сообщает об этом и показывает карточку назначенного наставника, если он известен. Кнопка "Сообщить" открывает форму с предложенной темой вопроса и редактируемым сообщением. Тема соответствует полю "вопрос", сообщение - полю "описание". Тикет создается по кнопке "Отправить наставнику". Прямая просьба в чате создать тикет также открывает черновик для подтверждения.

Повтор создания задачи или тикета с тем же ключом и теми же полями возвращает существующую запись с тем же ID. Повторное использование ключа с измененными полями возвращает конфликт. Просмотр и запись ограничены владельцем или получателем по правилам операций.

## 6. Wiki

Wiki выдает общие документы и документы команды пользователя. Доступ проверяется при поиске и при открытии прямой ссылки.

Wiki индексирует разделы внутренних документов. PostgreSQL хранит текст, заголовки, якоря и права доступа. Гибридный поиск объединяет полнотекстовую выдачу с поиском эмбеддингов через pgvector. Индексация и поиск используют одну модель эмбеддингов.

Инструмент `search_documents` вызывает REST API Wiki и возвращает до трех доступных фрагментов с названием документа, разделом и прямой ссылкой. При отсутствии подходящих фрагментов Wiki возвращает пустой список. Buddy формирует ответ, показывает карточку источника с цитатой и ссылкой на раздел. Для пустого результата работает сценарий обращения к наставнику.

## 7. Приемка

- Стажер открывает свой чат, историю, прогресс и документы команды. Наставник получает отказ в чате и открывает дашборд Tracker. Чужие диалоги, документы и прогресс закрыты.
- Поиск по ключевым словам и перефразировке возвращает доступные источники. Пустая выдача открывает путь к форме обращения. При отсутствии наставника форма не приводит к созданию тикета.
- Текст приходит частями. После разрыва SSE ответ продолжается, при переподключении текст и карточки отображаются без дублей.
- Создание задачи и тикета требует подтверждения. Повтор возвращает прежний ID. Неоднозначная команда завершения требует уточнения. После успешной отметки дашборд показывает новый статус при обновлении.
- Каждый Go-сервис проходит свои тесты. Покрытие по операторам строго больше 80% для каждого сервиса по профилю `go test -coverprofile`. Сбой любого сервиса виден в чате и допускает ручной повтор.

## Допущения

Имена маршрутов и формат JSON согласуются при реализации. Дедлайны считаются календарными датами. График наставника на макете можно показывать из явных демо-данных. Оценка среднего времени ответа требует данных и в контракт не входит.
