# Проверки backend — шаг 64

Автономные тесты, порог покрытия и чистка выполнены. Живая проверка Qwen
проведена; семантическая приёмка модели остаётся частичной (отклонения ниже).
Исходные MCP/SSE-изменения сохранены первым коммитом `3e53ae2`
(`feat(buddy): add task list and completion cards`, сообщение через `caveman-commit`).
На момент приёмки изменения оставлены без итогового коммита. Позже, в шаге 65,
они зафиксированы отдельными коммитами по команде пользователя.

## Автоматические проверки

- Полный `go test -race -count=1 -coverpkg=./... -coverprofile=... ./...` проходит.
  Тестам не нужны PostgreSQL/Ollama; пропусков из-за внешних сервисов нет.
- `go vet`, `go build`, `golangci-lint run` (0 замечаний),
  `golangci-lint fmt --diff`, Compose config и `git diff --check` проходят.
- Анализ `staticcheck` и `unused` выполнен через `golangci-lint`.
  Отдельный установленный `staticcheck` собран с Go 1.25.1 и не поддерживает
  экспортные данные Go 1.27; его ошибка совместимости не является результатом анализа.
- Проверка `scripts/check-coverage.py` принимает полный профиль и отклоняет
  порог 101% и профиль без `cmd/index`. Производственные команды не исключаются.

Все репозитории и сиды проверяются через настоящий `database/sql` с SQL-моком:
полный текст SQL, параметры, поля ответа, отсутствие записи, пустой список,
ошибки запроса, сканирования и итерации, закрытие строк. Сиды проверяют все
демо-записи, остановку на каждой ошибке вставки, begin/commit/rollback.
Wiki дополнительно проверяет кодирование векторов, массивы идентификаторов,
пустую синхронизацию и откат на каждом этапе.

HTTP-тесты сохраняют проверки валидации, лимита тела и лишних JSON-значений,
401/403/404/500, нормализации, авторства, уникальности ID, ответа и пустых списков.
Сквозные проверки handler → service → repository используют SQL-мок, а
handler → agent → MCP → service → repository сохраняют SDK и SSE:
карточка не пишет в БД, текстовое согласие не заменяет отдельный POST,
чужое завершение отклоняется, окончательные поля и автор берутся из POST
и доверенного контекста. Проверяются списки двух пользователей, пустая
карточка, доступ ментора к стажёру и ошибка записи/передачи SSE.

Команды имеют локальные зависимости и `run(ctx, deps) error`. В server отдельно
проверены сборка маршрутов и запуск/остановка HTTP. Проверки команд покрывают
успех, ошибки конфигурации/открытия/операций, отмену и закрытие БД;
seed проверяет порядок этапов и остановку после первой ошибки.

## Удалённый код и границы проверок

Удалены четыре помощника `testRepository`, создававшие схемы PostgreSQL и
применявшие миграции в тестах, `insertUser`, `insertMentorship`, `readChunks`,
а также зависимые от них интеграционные тесты и подготовка через переменную
тестового подключения. Значимые HTTP/SSE-сценарии перенесены в автономные тесты.
Проверки реального отката миграций, внешних ключей, CHECK/UNIQUE,
идемпотентности ON CONFLICT и расчёта статусов сервером PostgreSQL больше
не являются частью постоянной тестовой системы.

**SQL-моки не доказывают исполнение SQL и ограничений настоящим PostgreSQL.**
Реальные миграции, сиды, индекс и API проверены отдельно в живом прогоне.
Производственного мёртвого кода анализ не обнаружил; защитные проверки сохранены.
Go-код оформлен с разделением логических этапов, групп импортов и раздельными
типами; длинных строк свыше 120 символов не осталось.
Производственные SQL, миграции и HTTP/SSE-контракты сохранены.
Frontend и `backend-ai/` не менялись.

## Живой прогон

Использованы настоящий backend, `qwen3.5:4b` (`d8b0f5e9760c`, CPU,
контекст 16384), `embeddinggemma:300m` (`85462619ee72`) и PostgreSQL/pgvector 16.
Миграции, демо-сиды и штатная индексация выполнены в отдельной БД `buddy_live_64`
контейнера с tmpfs: 35 документов, 838 чанков и 838 реальных эмбеддингов.
Сиды создали 6 пользователей, 4 назначения, 12 задач и 8 тикетов;
для пустого списка и отсутствия ментора добавлен отдельный стажёр.

По просьбе пользователя системный промпт сокращён до 18 строк / 1844 символов
(примерно на 66% относительно промежуточного варианта с примерами).
Уточнены описания MCP-инструментов: область поиска, известный срок,
значение статусов и обязательный вызов подготовки карточки завершения.

Выявлен и исправлен узкий сбой передачи ошибки модели: PostgreSQL-сообщение
`relation "tasks" does not exist` Qwen принимал за пустой список. Агент теперь
передаёт `{"error":"Сбой инструмента. Действие не выполнено."}`;
технические подробности остаются в серверном логе. Регрессионный тест проверяет,
что успешный пустой список остаётся `tasks=[]`, сбой имеет отдельное поле error,
а SQLSTATE и сообщение PostgreSQL в контекст модели не попадают.

После последней правки повторена вся матрица; список задач, подготовка
завершения и ошибка инструмента выполнены по три раза. Дополнительно проверен
список второго выбранного пользователя. Всего в итоговой серии — 24 SSE-запроса
и пять отдельных POST. Промежуточные серии сохранены отдельно.

| Сценарий | Итог последней серии |
| --- | --- |
| Приветствие и общий вопрос | Краткий русский ответ, без инструментов и смайликов |
| Документация PostgreSQL | search_documents → attach_source; документ и содержательная цитата соответствуют ответу |
| Нет доступных документов | Сообщение об отсутствии информации, без источника; модель повторила успешный пустой поиск |
| Нерелевантные доступные фрагменты (дополнительная проверка) | Модель признала отсутствие информации, но прикрепила лишнюю карточку источника — отклонение |
| Свои задачи, 3 повтора | Во всех SSE-карточках правильные поля, порядок, пользователь и статусы; текст модели в одном повторе неверно пересказал дедлайн |
| Пустой список | `tasks=[]`, сообщение «У вас пока нет задач» |
| Известный срок | Карточка с `2026-11-20T18:30:00+03:00`; запись не создана |
| Неизвестный срок | Уточнены дата, время и пояс; инструмент не вызван, карточки нет |
| Тикет с ментором | Карточка с назначенным получателем, без записи до POST |
| Тикет без ментора | Явное сообщение о неудаче, карточки и записи нет |
| Завершение выбранной задачи, 3 повтора | list_tasks → prepare_task_completion; три карточки правильной задачи, статус до клика не изменён |
| Неоднозначная задача | Показан список; произвольная карточка не подготовлена, но прямой вопрос о выборе не задан — отклонение |
| Текстовое согласие | Подготовлена повторная карточка; записи и изменения completed нет; явное напоминание о кнопке пропущено |
| Роль ментора | Стажёрских MCP-инструментов нет, попытка вызова отклонена; POST завершения — 403; текст ответа общий, без пояснения роли |
| Изоляция пользователей | Чужие задачи не выданы; выбор intern.platform.1 даёт только его три задачи; чужой POST — 404 |
| Контролируемая ошибка SQL, 3 повтора | Во всех трёх ответах «Не удалось выполнить действие», без карточки задач и технических подробностей |
| Отдельный POST владельца | 200, completed=true подтверждён SQL; до POST задача не завершена |
| POST создания задачи и тикета | 201, окончательные поля сохранены, подставленный user_id проигнорирован |

Снимки всех задач и тикетов перед подготовкой карточек и после текстового
согласия полностью совпали. Поля карточек сохраняют данные сервера; точность
их свободного пересказа Qwen не гарантируется. Полную семантическую приёмку
`qwen3.5:4b` объявлять пройденной нельзя: остаются отклонения выбора источника,
уточнения и текста. Промпт сохранён коротким. По последнему указанию пользователя тонкая настройка
пропущена; температура и другие параметры генерации не менялись.

Исходные материалы находятся в `/tmp/buddy-validation-64/`:

- `live/` — итоговые запросы, полные SSE, сводки, отдельные POST и снимки БД;
- `model/` — реальные запросы/ответы Ollama, включая вызовы и результаты инструментов;
- `matrix-stdout.log`, `matrix.log` — последовательность сценариев и SQL-контроль;
- `server-final.log` — технические ошибки серверной стороны;
- `migrate.log`, `seed-final.log`, `index.log`, `database-counts.json`, `models.txt` — окружение и данные;
- `live-initial/`, `live-second/`, `live-short-initial/` — диагностические серии;
  `live-long-prompt-interrupted/` остановлена при переходе к короткому промпту.

Временные backend/прокси остановлены; два тестовых контейнера и БД в tmpfs
удалены. Volume `buddy-backend_ollama` с обеими моделями сохранён. Volume рабочей
БД не подключался. После удаления сервисов полный автономный race-прогон
выполнен ещё раз и прошёл без пропусков. Состояние очистки сохранено в
`cleanup.log` и `containers-after.txt`.
