# PostgreSQL: меняем схему поэтапно

> Данные в этом документе тестовые и вымышленные. Команда «Маяк», её процессы и примеры придуманы. Все совпадения с реальными лицами, организациями и событиями случайны. Документ не является регламентом Авито.

## Сначала обеспечиваем совместимость

Мы планируем изменение так, чтобы старая и новая версии приложения могли работать во время развёртывания. При замене поля сначала добавляем новое, выпускаем совместимый код и переносим данные. Затем переключаем чтение и только отдельным выпуском удаляем старое поле. Откат приложения возможен, пока схема и данные остаются с ним совместимыми.

Перед запуском мы оцениваем размер таблицы, активные транзакции, запас диска и ожидаемые блокировки. Большинство вариантов `ALTER TABLE` требуют `ACCESS EXCLUSIVE`, если документация не указывает иной режим. Поэтому даже короткую команду мы проверяем по [описанию ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html).

## Ограничиваем ожидание блокировки

Для учебной миграции мы задаём отдельные пределы ожидания блокировки и всей команды. Значения подбираем на копии данных; этот пример не служит универсальной настройкой.

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '30s';
ALTER TABLE articles ADD COLUMN summary text;
COMMIT;
```

При превышении лимита мы откатываем транзакцию и разбираем блокирующие сессии. Мы не перезапускаем миграцию бесконечным циклом. Различие параметров объясняется в [документации тайм-аутов PostgreSQL](https://www.postgresql.org/docs/current/runtime-config-client.html#RUNTIME-CONFIG-CLIENT-STATEMENT).

## Переносим данные небольшими порциями

Мы обновляем строки диапазонами первичного ключа, фиксируем прогресс и делаем обработку повторяемой. После каждой порции смотрим на задержку репликации, длительность запросов и нагрузку. Проверяем не только число заполненных строк, но и смысл новых значений на выборке.

Для большого индекса рассматриваем `CREATE INDEX CONCURRENTLY`: он допускает параллельные изменения строк, но требует дополнительных проходов и не выполняется внутри блока транзакции. При сбое может остаться невалидный индекс; перед повтором мы проверяем его состояние. Ограничения перечислены в [CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY).

## Подтверждаем завершение

Если подходит проверочное ограничение `CHECK`, мы можем добавить его с `NOT VALID`, исправить старые строки и выполнить `VALIDATE CONSTRAINT` отдельно. Новые изменения уже должны удовлетворять ограничению. Мы заранее описываем критерий остановки и ответственного за решение. Удаление данных не считаем автоматически обратимым: восстановление проверяем до выпуска в рамках [эксплуатационной готовности](../platform/operational-readiness.md).
